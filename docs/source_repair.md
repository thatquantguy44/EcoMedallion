# Staged FRED source repair

The explicit operator workflow in `scripts/repair_marketatlas_fred.py` repairs a
bounded observation window using authoritative FRED real-time intervals. It is
separate from normal pipeline runs. Staging makes API requests and writes local
captures only. `apply` writes only to the configured localhost PostgreSQL warehouse
(`macro_medallion`, port 55432) after validating staged checksums and intervals.

For the approved MarketAtlas selection, pass the generated review manifests:

```sh
python scripts/repair_marketatlas_fred.py stage \
  --manifests /absolute/path/freshness-review.yml /absolute/path/vintages-review.yml \
  --output data/source-repair/RUN_ID --end YYYY-MM-DD \
  --series AKUR,GDP,ANFCI
python scripts/repair_marketatlas_fred.py apply \
  --output data/source-repair/RUN_ID --series AKUR,GDP,ANFCI
```

The current staging manifest format is the JSON-form YAML generated by
MarketAtlas; ordinary upstream YAML manifests remain handled by the normal CLI.
The default start is 2024-01-01. Each series is limited to 100,000 coalesced
versions; each API window to one million raw observations. Extraction runs at
60 requests/minute, with one retry and explicit timeouts. Failed/empty/invalid
captures are quarantined. Inspect the complete manifest and failure list before
applying; a completed staging command can contain quarantined series.

The utility always requests complete vintage history **for the bounded observation
window**. It validates identifiers, source identity, finite/missing values, date
order, non-overlapping vintages and open final validity intervals. It never uses
capture time or observation periods as availability. Checksummed captures can be
resumed without API re-pulls. Resume only from trusted local files.

For each applied series, a transaction locks the source, rejects post-capture
source changes, archives the old metadata and all affected Silver/latest/revision
rows, replaces only the chosen window, rebuilds its two small Gold projections,
sets vintage tracking and writes success lineage. Original rows remain in
`audit.fred_repair_backup`, referenced by `audit.fred_repair_batch`. Reapplying the
same capture is a no-op. The missing revision-table index is created concurrently
before the rollout so per-series operations avoid repeated full-table scans.

The source reader is not used for repair writes. Credentials are resolved using
the existing upstream warehouse configuration and environment and never appear
in manifests or command output. The utility does not initialize unrelated tables,
rebuild other Gold models, invoke ECB ingestion or send notifications.

To reverse a specific applied series/window:

```sh
python scripts/repair_marketatlas_fred.py restore --batch-id BATCH_ID
```

Restore refuses to overwrite Silver records changed by a newer run. It restores
the backed-up Silver/Gold rows and metadata and marks the ledger restored while
retaining the backups/audit trail. Review later dependent publications before a
rollback. Keep the original source rows/captures under the existing restricted
internal retention policy; no automatic backup pruning is configured.

When changing a current-only series to vintage tracking, update its canonical
manifest as well as the database metadata. Enable `complete_vintage_history` for
the operator's upstream configuration so later pulls retain complete known
intervals. Older observations outside the repaired window are unchanged and can
still have unknown availability; do not claim full-history recovery.

The FRED client paginates observation rows in ordinary calls, vintage-cap fallbacks
and complete-history windows. It preserves an open final real-time interval and
uses contiguous window boundaries; equal values across an unknown gap are not
coalesced. One slot is reserved for FRED's possible boundary state under the
2,000-vintage API cap. FRED series whose latest stored observation period exceeds
the existing frequency-age threshold bypass cadence skipping; fresh FRED series
and other providers retain their existing cadence behavior. This does not create
or enable an upstream ingestion schedule.
